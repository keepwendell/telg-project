# 前端技术栈演进评估（Frontend Stack Evolution）

> 版本：2026-09-18 · 状态：planned（远期演进方向，未排期）
> 关联：《架构规划书 v1.0》第 19/20 节 · `docs/架构/architecture-总体架构.md` · `docs/规划/roadmap-待办事项.md`

## 1. 背景

《架构规划书 v1.0》建议前端采用 **React + TypeScript + Vite + React Router + Zustand + CSS Modules**。当前实际实现为**单文件原生 JS**（`frontend/index.html`，无构建步骤）。本文评估该技术栈选型是否值得纳入规划。

## 2. 现状基线（2026-09-18）

| 指标 | 数值 | 含义 |
|---|---|---|
| `frontend/index.html` | 445 KB / 7,139 行 | HTML + CSS + JS 全内联 |
| `frontend/onboarding.html` | 786 行 | 首启引导页 |
| 函数数量 | ≈396 | 全部在单一作用域 |
| DOM id 数量 | ≈308 | 全局标识符 |
| 构建链 | 无 | 后端 uvicorn 同源托管静态文件 |
| 测试 | Playwright e2e（3 个文件） | 全链路回归基线 |

## 3. 迁移收益（支持规划书方案）

1. **类型安全**：近几轮线上缺陷集中于字段语义/状态同步（difficulty/depth 错位、answer 字符串契约、speakerId 回退）。TS 类型 + 后端 Pydantic 契约同步可在编译期拦截这一类错误。
2. **组件化可维护性**：单文件无模块边界，功能新增互相干扰风险随规模线性上升；组件化降低修改半径。
3. **测试基础设施**：组件测试 + 类型检查反馈快于全量 e2e。
4. **多端演进基础**：桌面（Tauri）/ 移动（React Native / Expo）可复用逻辑与类型。
5. **生态与工具链**：路由、状态管理、懒加载、代码分割等成熟方案。

## 4. 迁移成本（反对立即做的理由）

1. **整体重写**：单文件无模块边界，不存在渐进迁移路径；约 7k 行 UI 逻辑需重写，期间需冻结功能或双轨维护。
2. **零用户可见收益**：当前功能稳定，迁移为纯成本投入。
3. **构建链复杂度**：引入 Node / Vite / CI，部署从"Python 单进程托管"变为多阶段构建产物。
4. **回归风险**：现有 Playwright e2e 选择器（.lib-item 等）需适配；UI 细节（明暗主题、i18n、弹窗交互）回归面大。
5. **违背"简单优先"原则**：规划书 2.1 明确"不为未来可能需要建立大量抽象层"。

## 5. 结论

**方向合理，时机未到。**

- 收益集中在**工程长期可维护性**与**多端演进准备**，不改变任何用户可见行为；
- 触发迁移前，先满足下述任一触发条件，避免为"可能"提前付出成本。

## 6. 触发条件（任一满足即启动迁移评估）

| # | 触发条件 | 判定口径 |
|---|---|---|
| 1 | 核心功能模块继续扩张 | 新增 ≥2 个独立功能模块（如生词本、错题本、多语言）后，单文件修改冲突/回归频次明显上升 |
| 2 | 多端需求立项 | 桌面端或移动端进入规划排期 |
| 3 | 契约回归成本过高 | 单次字段契约变更导致线上回归修复成本显著上升（以最近 difficulty/depth 错位为基准） |

## 7. 迁移范围界定（触发后执行）

- **只重写前端表现层**：参数收集、渲染、播放器、素材库、设置；
- **后端不动**：API / Artifact 数据契约 / Prompt 链路 / TTS / SQLite 全部保持；
- **契约优先**：以《设计说明书 v2.x》字段语义为唯一类型来源，前端 TS 类型从后端 Pydantic 对齐生成；
- **回归基线**：现有 Playwright e2e 全部通过后再切换入口。

## 8. 阶段

1. 迁移评估（触发条件满足时）：工作量估算、组件拆分方案、e2e 适配清单；
2. 冻结功能：重写期间不接受新功能；
3. 重写前端：React + TS + Vite，页面结构沿用 Generator / Player / Library（+ Settings）；
4. e2e 回归：三条 e2e 全绿后切换；
5. 观察期：2 周双通道（保留单文件版本可回退）。

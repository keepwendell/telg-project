## 事项 1：词级时间戳与词级同步（卡拉 OK 高亮/跟读）

### 背景

当前时间戳链路（已实施）：

```
逐句 TTS 合成 → probe 整句时长 → start += dur + 400ms gap → 句级 start_ms/end_ms
```

句子级已满足：点击跳句、句高亮、单句循环、倍速。**短板**：无法做"词级高亮"（语音读到哪个词、听读跟读、单词精准定位重听），这类体验需要词级时间戳。

### 兼容性核心设计：引擎无关增强管线

卡拉 OK 与噪音叠加要"兼容各种 TTS"，靠的不是让每个引擎都实现，而是**把增强层从引擎里剥出来**：

```
TTS 引擎（各自实现，只"出声"）
  synthesize(text, voice, rate) → WAV (24k mono)
        ↓ 统一接口
引擎无关增强管线：
  ① 句级时间戳：probe 时长 + gap（已有）
  ② 拼接 merge_mp3（已有）
  ③ 词级对齐 WordAligner → words[]（本事项）
  ④ 噪音叠加 NoiseMixer（事项 2，混音不改时长）
        ↓ 统一数据格式（words + start_ms/end_ms）
前端播放器（词级高亮/跳句/循环，不知道引擎是谁）
```

新增任何 TTS 引擎 = 只实现 `synthesize_seg`，自动获得卡拉 OK + 噪音能力。

### 词级时间戳三层策略（能力向上兼容）

| 层级 | 适用引擎 | 来源 | 精度 |
|---|---|---|---|
| ① 原生时间戳（最准、零成本） | edge-tts（WordBoundary）、阿里云百炼（enableWordTimestamp） | 合成时直接采集 | 引擎级 |
| ② 对齐器后处理（兜底、统一） | Kokoro、硅基流动等一切无时间戳引擎 | Qwen3-ForcedAligner-0.6B 对"音频+已知文本"离线对齐 | ±20ms |
| ③ 降级 | 对齐器未安装 | 前端退化为句级高亮 | — |

**关键：后端无论走哪层，都输出同一种 `words[{w, start_ms, end_ms}]` 存 DB，前端只认这一个格式。** 引擎能力差异只影响"精度档位"，不影响"功能有没有"。

### TTS 原生时间戳能力核查（2026-09-16）

| 方案 | 原生时间戳 | 级别 | 备注 |
|---|---|---|---|
| edge-tts | ✅ | 词级 | WordBoundary 事件流（offset/duration per word），当前工程未采集 |
| Kokoro（kokoro-onnx） | ❌ | 无 | 仅返回 PCM 音频，无任何时间信息 |
| 硅基流动 TTS | ❌ | 无 | API 仅返回 `{audio_url, duration_ms}` |
| 阿里云百炼 CosyVoice3.5 / Qwen-Audio TTS | ✅ | 字级 | `enableWordTimestamp=true`，仅流式输出模式 |
| Azure Speech（edge-tts 正式版） | ✅ | 词级+句级 | WordBoundary + SentenceBoundary |
| Qwen3-ForcedAligner-0.6B | 对齐工具 | 词级 | "音频+已知文本 → 词级时间戳"，精度 ±20ms，离线，0.6B |

### 影响面（若实施）

- 后端：`dialogue_segments` 增加词级存储（words JSON 列或独立表）；走"原生 → 对齐器 → 降级"三层策略写入。
- 前端：transcript 行内词级高亮渲染；播放时按 `words[i].start_ms` 驱动当前词定位（复用现有 100ms tick）。
- 播放器：`seekSentence` 不变（句级跳转仍以句时间戳为准），词级仅用于高亮与跟读。

### 建议

采用**路径 ③ 分层**：原生时间戳优先（edge-tts/百炼），无则走 Qwen3-ForcedAligner 对齐（P1，离线 +0.6B 模型依赖），对齐器缺失时前端降级句级高亮。不阻塞当前任何功能。

### 实施计划（含 POC 验证 gate）

对齐器"能保证吗"不能拍胸脯——三个风险点：① 文本规范化不一致（"3.8 degrees" vs "three point eight degrees"）；② 对齐器在真实语音上训练、对合成语音的鲁棒性未验证；③ 句内空白/符号归属。**因此第一步是 POC 验证，通过后才全量接入**：

1. **P0 验证（gate）**：
   - ground truth：edge-tts 合成一篇对话，采集其原生 `WordBoundary` 词边界（引擎级精度）作为标准答案；
   - 同一文本用 Kokoro（及候选的硅基流动）合成，跑 Qwen3-ForcedAligner 对齐；
   - 量化偏差：对比两套词边界（同文本同语义），统计偏差分布（均值 / P95 / 最大偏移），抽样人工听感确认；
   - 判定：**P95 < 150ms 且无系统性错位 → 全量接入**；否则对无原生时间戳引擎降级句级高亮。
2. **工程兜底（无论 POC 结果都要有）**：
   - 对齐质量自检：词时间戳应无缝覆盖整句（无大空隙 / 重叠 / 越界），启发式校验失败 → 该句自动降级句级；
   - 规范化文本优先：TTS 侧若能拿到规范化后文本（实际读音）优先作为对齐输入，消除风险 ①。
3. **分层落地**：POC 通过后 → `dialogue_segments` 增加 words 存储 → 三层策略写入 → 前端词级渲染（复用 100ms tick）。

## 事项 2：环境噪音叠加（SNR 混音）

### 动机

听力训练缺"嘈杂环境"难度档：Level 4-5 应模拟真实工作场景（办公室/咖啡馆/工厂/风声），检验在干扰下的理解能力。

### 与引擎的兼容性

- 叠加发生在**拼接后的完整音频**上（PCM 域/ffmpeg 混音），任何 TTS 引擎的产物等价 → **天然引擎无关**。
- **不改时长** → 句级、词级时间戳全部保持有效，无需重算。
- 噪声源两种：程序生成白/粉红噪声（numpy，零依赖），或环境音样本（`backend/storage/noise/` 提供 3-5 个样本）。
- 混音参数：噪声类型 + SNR（dB），存 meta，重新合成时应用。

### 实现要点

- 后端新增 `NoiseMixer.mix(audio, noise, snr)`：`alpha = 10^(-SNR/20) × 语音RMS / 噪声RMS`，PCM 域叠加。
- **顺序约束：先对齐（词级时间戳）→ 再混音**。先混音再对齐会因噪声干扰降低对齐精度；混音不改语音时间位置，两者结果一致。
- 前端生成设置加"环境噪声"选项（无/白噪声/粉红噪声/环境样本 + SNR 滑块），meta 持久化。
- 播放器、时间戳链路零改动。

### 工作量

后端 0.5-1 天 + 前端选项 0.5 天。可与事项 1 并行（互不依赖）。

## 事项 3：领域自定义（产品方向 · 领域开放）

### 产品动机

当前领域（Automotive / Embedded / AD / Robotics / Power Electronics）、角色、场景全部是**硬编码下拉**，产品被锁定在"汽车+嵌入式"这个小圈子。定位要升级为通用"技术英语听力"工具时，领域必须开放给用户自定义：半导体、新能源、医药研发、金融工程、法律合规、航空航天……任意工程领域。

### 现状约束分析

| 链路 | 现状 | 评估 |
|---|---|---|
| 前端参数 | `domain-select` / `role-select` / `scenario-select` 硬编码 option | 需开放自由文本输入 |
| 后端 schema | `GenerateIn` 的 domain/role/scenario 已是任意字符串（非枚举） | ✅ 无障碍 |
| LLM | prompt 中 domain/role/scenario 参数化注入；通用模型可生成任意领域对话 | 主要工作是**验证自定义领域的技术术语质量**（幻觉/术语不准确风险） |
| **Mock 链路** | `mock_generate` 用关键词匹配（tire/can/torque）映射 3 个种子素材，自定义领域无法匹配 | **主要障碍**——需"通用模板兜底"（已有 TEMPLATE_DIALOGUE 兜底分支，但内容偏模板化，需评估） |
| 词汇/问题/句型 | 均由 LLM 生成，无硬编码 | ✅ |

### 方案

1. **前端**：参数区"Domain"下拉改为"下拉常用领域 + 自定义输入"双模式（选择或自由输入）；Role / Scenario 同理（或与领域联动，由 LLM 按领域生成推荐角色/场景）。
2. **LLM**：prompt 显式要求"按用户给定的领域/角色/场景生成，术语必须符合该领域惯例"；对自定义领域增加**术语自查指令**（生成后模型自检专业术语准确率）。
3. **Mock 兜底**：`mock_generate` 关键词匹配失败时走通用模板分支（已存在），把 topic 注入模板；验收标准=自定义领域在 Mock 模式下也能产出结构完整的语料。
4. **样本验证**：真实 LLM 下用 3 个非预设领域（如 Semiconductor Lithography / Grid Energy Storage / Medical Device Validation）各生成 1 篇，人工检查术语正确性与对话自然度。

### 影响面

- 前端：`collectParams` / 生成面板参数区（新增自由文本）
- 后端：`mock_generate` 兜底分支微调；prompt 模板加"自定义领域"约束
- 零影响：TTS、时间戳链路、播放器

### 工作量

前端参数区 0.5d + prompt/LLM 验证 1d + mock 兜底 0.5d。依赖：真实 LLM 链路可用（否则只能用 Mock 验证结构）。

## 事项 4：多语言学习素材（产品方向 · 语言扩展，日语优先）

### 产品动机

当前素材固定为"英文对话 + 中文翻译"（`text_en` / `text_zh`）。用户希望学习语言可扩展，**日语优先**（技术日语听力场景，如汽车/半导体日系企业环境），德语后续。

> **关键区分**：界面语言（UI i18n，已有 en/zh）≠ **学习素材语言**（本事项指后者：对话正文语言 + 翻译语言）。

### 现状约束分析

| 链路 | 现状 | 评估 |
|---|---|---|
| 数据模型 | `dialogue[].text_en/text_zh`、`vocabulary[].en/zh`、questions 等全部 en/zh 双列 | 需泛化为"目标语言对"（如日文正文 + 中文翻译） |
| 数据库 | `dialogue_segments` 表 text_en/text_zh 列 | 需 schema 迁移或扩展列 |
| LLM | DeepSeek 等支持日语/德语生成 | prompt 按 (学习语言, 翻译语言) 参数化；**一次调用同时产出两种语言**（上下文一致性更好、成本低于两次调用） |
| **TTS（硬约束）** | 当前主力 Kokoro **仅英文 10+ / 中文 5 个音色，无日语/德语**；edge-tts 有 ja-JP（Nanami/KeitaNeural）、de-DE（Katja/ConradNeural） | 日语素材需切 edge-tts 或新增日语引擎；**引擎选择必须与素材语言联动**（语言 → 可用音色池过滤） |
| 时间戳链路 | 引擎无关（probe + gap 累加） | ✅ 无障碍 |
| 前端 | `transcriptHTML` 渲染 text_en/text_zh、翻译切换按钮固定 "CN"、MD 导出双语 | 需泛化：翻译按钮变多语言切换、素材带语言标签 |

### 方案

1. **数据模型**：dialogue / vocabulary / questions 文本字段从"en/zh 双列"泛化为**语言对**（`lang_pair = {target, translation}`，如 `ja/zh`、`ja/en`、`de/zh`），兼容现有 en/zh 数据（迁移或降级读取）。
2. **LLM**：生成设置新增"学习语言 / 翻译语言"选择；prompt 按语言对参数化，**一次调用同时产出目标语言正文 + 翻译**。
3. **TTS**：素材语言与引擎/音色联动——选日语 → 音色池过滤为 ja-JP（edge-tts）；Kokoro 无日语时该引擎对日语素材不可选（UI 置灰 + 说明）；德语同理。
4. **前端**：翻译切换按钮泛化（CN → 目标翻译语言）；transcript / 导出 MD 按语言对渲染；素材列表与详情显示语言标签（EN / JP / DE）。

### 优先级与顺序

- **日语 P1**（技术日语听力是明确需求）；**德语 P2**（延后，机制相同只是加语言对与音色池）。
- 建议先做**数据模型泛化 + LLM 语言对**（不依赖 TTS 即可验证语料质量），再做 TTS 音色联动与前端泛化。

### 影响面

- 后端：schema 迁移、prompt 语言对、TTS 引擎-语言映射、mock 模板语言化
- 前端：生成设置语言选项、transcript 渲染、翻译切换按钮、导出
- 零影响：播放器/时间戳/词级规划（事项 1）链路

### 工作量

数据模型 + 迁移 0.5d、LLM 语言对 prompt 0.5-1d、TTS 音色联动 0.5d、前端泛化 1d；日语端到端验证另计 1d。

## 事项 5：LLM Prompt 系统性调优（产品方向 · 生成质量）

### 动机

生成素材的质量上限由 prompt 决定——同样的模型与参数，prompt 好坏直接决定术语准确度、对话自然度与结构通过率。当前 prompt 是功能开发期一次成型的，存在多处可系统优化的点，且**没有任何评测机制**（prompt 改坏了无法及时发现）。

### 现状诊断（2026-09-16 代码走查，`backend/main.py`）

| 维度 | 现状 | 问题 |
|---|---|---|
| 定位 | `LLM_SYSTEM_PROMPT` 硬编码"面向汽车、智能驾驶、底盘控制、控制算法与嵌入式软件等研发工程师" | 与事项 3（领域自定义）冲突——自定义领域时定位文案不匹配 |
| JSON 示例 | 输出格式示例中字段后带中文注释（`// 英文：...`） | **严格 JSON 不允许注释**——示例写法可能诱导模型输出注释导致解析失败（虽有 3 次重试兜底，但每次失败都烧 token 与延迟） |
| 输出长度 | `client.chat.completions.create` 未设 `max_tokens` | 长对话（long / Level 4-5）可能被模型自行截断，靠重试兜底 |
| 用户 prompt | `build_user_prompt` 仅 6 行（Topic/Domain/Role/Scenario/Difficulty/Length） | 过简——未传递领域专业知识提示、目标听众、翻译要求等 |
| 校验 | pydantic + `validate_extra`（词数 3 倍上限、≥3 句、无中文、词汇≥4、问题≥2、句型≥2）+ 3 次带错误反馈重试 | 校验面较全 ✓；但错误反馈只是机械拼接，无"JSON 修复专用重试"（把 raw 原文给模型修） |
| 模型适配 | 单一 prompt 适配所有 OpenAI 兼容模型（DeepSeek/Qwen/豆包/Kimi/Ollama） | 不同模型指令遵循度不同（尤其 Ollama 小模型对中文长指令敏感） |
| 温度 | 整体 `temperature=0.7` | 背景/对话（创意）与词汇/问题（确定性）共享同一温度，无分层策略 |
| **评测** | 无 | **最大缺口**——没有固定评测集与指标，prompt 任何改动都无法客观验证优劣 |

### 调优方向

1. **结构分层与精简**：system prompt 拆为"角色与任务 / 输出格式 / 质量要求 / 参数定义"四段，压缩冗余说明（目标压缩 30-40%）；**JSON 示例去掉注释**并显式声明"示例仅供参考，输出必须是合法 JSON，不得包含注释"。
2. **参数化（与事项 3 / 4 联动）**：定位文案按用户 domain 动态生成（自定义领域时注入"领域专家"角色）；语言对参数化（事项 4：日文正文 + 中文翻译的指令、术语译法要求）。
3. **工程补漏**：设置 `max_tokens`（按 length 档位估算，如 120s≈1400 / 240s≈2600）；新增"JSON 修复重试"分支（解析失败时把模型原始输出原文喂回，令其只修不重写）。
4. **评测与回归（关键）**：
   - 固定评测集：10 篇主题（覆盖 5 个预设领域 + 3 个自定义领域 + 2 个多语言），各配期望指标；
   - 指标：结构通过率（首轮 JSON 解析成功率）、词数偏差（相对 target_words）、术语合理性（抽查）、自然度（人工 1-5 分）、token 成本（prompt+completion）；
   - 建立 `backend/tests/prompt_evals/` 目录存放评测集与结果快照，prompt 每次修改跑一遍回归，结果对比存档。
5. **多模型适配（P2）**：按模型族提供 prompt 变体（如 Ollama 用更短指令 + 更强约束）；温度策略：可评估"双调用"（背景/对话 temp 0.8 + 词汇/问题 temp 0.3）的成本收益，不划算则保持单调用。

### 影响面

- 后端：`LLM_SYSTEM_PROMPT` / `build_user_prompt` / `call_llm_with_retry` / `validate_extra` 微调；新增评测脚本与固定评测集
- 前端：零改动（prompt 变更对 UI 透明）
- 与事项 3（领域参数化）、事项 4（语言对）存在共享改造点——建议**在 3/4 落地后统一做一次 prompt 重构**，避免重复返工

### 优先级与顺序

- **P0（可独立先行）**：max_tokens、JSON 注释风险、system 精简——低风险高收益，不依赖 3/4
- **P1**：评测集与回归机制（prompt 工程的基础设施，先于大改）
- **P1**：领域/语言参数化（随事项 3/4 一并落地）
- **P2**：多模型适配层、温度分层策略

### 工作量

P0 工程补漏 0.5d；评测集 + 回归脚本 1d；参数化重构 0.5-1d（随 3/4）；多模型适配另计 1-2d（P2）。

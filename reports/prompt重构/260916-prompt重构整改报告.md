> 范围：`LLM_SYSTEM_PROMPT` / `build_user_prompt` / `call_llm_with_retry` / `DIFFICULTY_DEFS` 四个模块的 prompt 工程化重构。**前端零改动**（所有设置选项、参数值域、控件形态不变，仅后端"如何使用参数"变化）。

## 一、现状诊断（重构前，2026-09-16 代码走查）

| # | 问题 | 严重度 | 说明 |
|---|---|---|---|
| 1 | 定位硬编码 | 中 | System 写死"面向汽车、智能驾驶…"，与 roadmap 事项 3（领域自定义）直接冲突 |
| 2 | **JSON 示例带 `//` 注释** | 高 | 严格 JSON 不允许注释；示例写法可能诱导模型输出注释 → 解析失败，只能靠 3 次重试兜底（白烧 token 与延迟） |
| 3 | **无 `max_tokens`** | 高 | 长对话（180/240s）可能被模型自行截断，靠重试兜底 |
| 4 | user prompt 过简 | 高 | 仅 6 行字段填空（Topic/Domain/Difficulty/Length…），模型不理解"为什么生成"，对话空泛的根源 |
| 5 | System 含动态占位符 | 中 | 7 处 `.replace()` 每次请求改写 system → DeepSeek context caching 无法命中稳定前缀 |
| 6 | 难度定义为形容词 | 中 | "术语密集"、"复杂从句"不可度量，模型无法执行 → 难度档位形同虚设 |
| 7 | 失败反馈机械 | 低 | 重试时把 pydantic 错误列表原样拼接，模型可能整篇重写，费 token 且成功率低 |

## 二、重构方案（设计决策）

### 2.1 核心原则：System 静态化 + User 简报化

```
System（完全静态，无占位符，吃 provider context caching）
  角色定位 → 输出契约（JSON 骨架，去注释）→ 质量红线（按优先级）→ 对话结构规则
User（每次动态组装，需求简报）
  本次任务（主题/领域/角色/场景/语气）→ 生成约束（参数可执行化）→ 对话看点
```

### 2.2 六项改动明细

| 改动 | 内容 | 收益 |
|---|---|---|
| **A. System 静态化** | 删除全部 7 处 `.replace()` 占位符；领域定位文案移除，改为"为研发工程师生成"，具体领域由 User 消息注入 | system 前缀稳定 → context caching 命中；为事项 3 领域自定义铺路 |
| **B. JSON 去注释** | 输出契约中所有 `// 中文注释` 移除，改为字段值占位说明（如 `"technical_background": "英文：该主题工程背景，2-3 句"`）；显式声明"JSON 示例仅供参考，输出时不得包含注释" | 降低模型照抄注释导致解析失败的概率 |
| **C. user prompt 简报化** | 从 6 行字段填空 → "需求简报"：任务意图 + 本次任务五元组 + 生成约束 + 对话看点；新增**领域语境指令**（"必须符合该领域研发工程师的真实语境与术语惯例"） | 模型理解生成意图；对话自然度与领域术语准确性提升 |
| **D. 对话看点（模型自推）** | 新增"## 对话看点"段：要求模型根据主题自行确定一个最有价值的讨论焦点（权衡/故障排查/评审分歧），对话围绕焦点展开有张力 | 根治"平铺直叙罗列知识点"的教科书腔；前端零改动（不新增输入项） |
| **E. 难度参数可执行化** | `DIFFICULTY_DEFS` 重写：每档给出**技术词汇密度百分比 + 句长范围 + 复合从句层数上限**三个可度量约束（Level 1 约 10% 术语 → Level 5 约 65%） | 难度档位真正可执行、可评测 |
| **F. 工程补漏** | ① `max_tokens = target_words × 9 + 800`（60s→2060 / 120s→3410 / 240s→6020，防截断且不过量）；② 重试反馈改为**修复指令**："请只修正上述问题、保留其余内容，重新输出完整 JSON" | 防截断；重试成功率提升、省 token |
| G. regenerate 区分 | `build_user_prompt(p, action)`：action=regenerate 时注入"更换切入角度或结构，内容与上一版不雷同" | refine 与首轮生成产出差异化 |

## 五、遗留项与后续

1. **真实 LLM 回归（唯一未验证项）**：沙箱无真实 API key，真实生成质量（自然度/术语/首轮 JSON 通过率）需用户本机配置 key 后对比验证。**建议对比同一主题：旧版 vs 新版**（如"质心侧偏角估算"120s Level 3），重点看对话是否围绕一个焦点展开、是否有讨论张力。
2. **评测集建立**（roadmap 事项 5 P1）：本次重构是"prompt 工程化"第一刀，后续需固定 10 篇评测主题 + 指标（首轮 JSON 通过率 / 词数偏差 / 术语抽查 / 自然度 / token 成本），prompt 每次改动跑回归。
3. **领域参数化**（事项 3）落地时：System 已静态化，领域只需在 User 简报中注入，无需再改 System——本次重构已为其铺路。
4. **多语言**（事项 4）落地时：语言对指令只需加在 User 简报"生成约束"段。
5. 旧版 prompt 如需对比，可在 git history 中取 `899a2b5` 之前的 `main.py`。
